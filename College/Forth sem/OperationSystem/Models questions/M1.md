### 1. Define Operating System. Explain objectives of Operating System. [1+4]

**Definition (1 mark):**
An **Operating System (OS)** is system software that acts as an intermediary between the computer user/application programs and the computer hardware. It manages hardware resources (CPU, memory, I/O devices, storage) and provides a convenient, efficient environment for executing programs.

**Objectives of an Operating System (4 marks):**

1. **Convenience** – Makes the computer system easier and more convenient to use by hiding hardware complexity from the user.
2. **Efficiency** – Ensures efficient utilization of hardware resources such as CPU, memory, and I/O devices.
3. **Ability to Evolve** – Allows effective development, testing, and introduction of new system functions without interfering with existing services.
4. **Resource Management** – Manages allocation and de-allocation of resources among multiple users/processes fairly and securely.
5. **Throughput and Response Time** – Maximizes throughput (jobs done per unit time) and minimizes turnaround/response time.

### 2. How can we solve the producer-consumer problem using semaphore?

The **producer-consumer problem** involves two processes sharing a fixed-size buffer: the *producer* generates data and places it in the buffer, and the *consumer* removes data from it. The problem is to ensure the producer doesn't add data when the buffer is full and the consumer doesn't remove data when it's empty, while also avoiding race conditions.

**Semaphores used:**
- `mutex` (binary semaphore, initial value 1) — ensures mutual exclusion on the buffer
- `empty` (counting semaphore, initial value = n) — counts empty slots
- `full` (counting semaphore, initial value = 0) — counts filled slots

**Producer:**
```
do {
    // produce an item
    wait(empty);
    wait(mutex);
        // add item to buffer
    signal(mutex);
    signal(full);
} while(true);
```

**Consumer:**
```
do {
    wait(full);
    wait(mutex);
        // remove item from buffer
    signal(mutex);
    signal(empty);
    // consume the item
} while(true);
```

`wait()` decrements the semaphore (blocking if it would go negative) and `signal()` increments it, allowing safe synchronization between the producer and consumer without race conditions.

### 3. What do you mean by Preemptable and Non-Preemptable resources? Describe the necessary conditions for deadlock. [2+3]

**Preemptable vs Non-Preemptable Resources (2 marks):**
- A **Preemptable resource** can be taken away from a process without any ill effect (e.g., CPU, main memory). The process can resume later without loss of correctness.
- A **Non-preemptable resource** cannot be taken from its holder without causing the operation to fail or the process to malfunction (e.g., printer, tape drive, disk drive during a write operation).

**Necessary Conditions for Deadlock (3 marks):**
A deadlock can occur only if all four of the following conditions hold simultaneously:

1. **Mutual Exclusion** – At least one resource is held in a non-shareable mode; only one process can use it at a time.
2. **Hold and Wait** – A process holding at least one resource is waiting to acquire additional resources held by other processes.
3. **No Preemption** – Resources cannot be forcibly removed from a process; they must be released voluntarily.
4. **Circular Wait** – A set of processes {P0, P1, ..., Pn} exists such that P0 waits for a resource held by P1, P1 waits for P2, ..., and Pn waits for a resource held by P0.

### 5. What is meant by system threat? Explain different types of program threat.

**System Threat:**
A **system threat** is any potential danger that can misuse system resources, damage system operations, cause loss of data/confidentiality, or disrupt services provided by an operating system. Threats generally exploit vulnerabilities in the OS to gain unauthorized access or disrupt normal functioning.

**Types of Program Threats:**

1. **Trojan Horse** – A program that hides malicious code inside a seemingly legitimate/useful program; often used to steal passwords or create backdoors.
2. **Trap Door (Backdoor)** – A hidden entry point in a program, deliberately left by the designer, that bypasses normal security checks.
3. **Logic Bomb** – Malicious code that lies dormant and executes only when a specific condition (date, event) is met.
4. **Virus** – A self-replicating piece of code that attaches itself to legitimate programs and spreads when the infected program runs, potentially corrupting or deleting data.
5. **Worm** – A standalone self-replicating program that spreads across networks without needing to attach to a host program, often consuming bandwidth/resources.

### 6. Explain methods of communication in a distributed system.

In a **distributed system**, processes on different machines communicate over a network. The major communication methods are:

1. **Message Passing** – Processes communicate by explicitly sending and receiving messages using primitives like `send()` and `receive()`. Can be direct (naming the sender/receiver) or indirect (via mailboxes/ports).
2. **Remote Procedure Call (RPC)** – Allows a process to call a procedure that executes on a remote machine as if it were a local call; the underlying network details are hidden from the programmer.
3. **Remote Method Invocation (RMI)** – The object-oriented equivalent of RPC, used in distributed object systems (e.g., Java RMI) to invoke methods on remote objects.
4. **Sockets** – Low-level communication endpoints (IP address + port) that allow processes on different hosts to exchange a stream of bytes over TCP/UDP.
5. **Shared Memory (Distributed Shared Memory - DSM)** – Provides an abstraction of shared memory across machines that don't physically share memory, synchronized via the network.

### 7. Short Notes (Any Two)

**a) Access Control Matrix**
A conceptual model used for protection in operating systems. Rows represent **domains** (users/processes) and columns represent **objects** (files, devices, resources). Each cell `access(i, j)` lists the operations (read, write, execute) that domain *i* can perform on object *j*. It's typically implemented via **Access Control Lists (per-object)** or **Capability Lists (per-domain)** since the full matrix is usually sparse.

**b) Process States**
A process moves through several states during its lifetime:
- **New** – Process is being created.
- **Ready** – Process is waiting to be assigned to the CPU.
- **Running** – Instructions are being executed by the CPU.
- **Waiting/Blocked** – Process is waiting for some event (e.g., I/O completion).
- **Terminated** – Process has finished execution.

Transitions occur as: New → Ready → Running → (Waiting ⇄ Ready) → Terminated.

**c) Kernel**
The **kernel** is the core part of the operating system that has complete control over the system. It manages CPU scheduling, memory management, device management, and system calls, acting as a bridge between applications and hardware. It runs in **kernel mode** (privileged mode) and is loaded into memory first at boot time, remaining resident for the system's lifetime.

### 10. Disk Access Time, Disk Response Time & Disk Scheduling [2+8]

**Disk Access Time (2 marks, part 1):**
The total time taken to access data from the disk:
**Disk Access Time = Seek Time + Rotational Latency + Transfer Time**
- *Seek Time*: time for the read/write head to move to the correct cylinder/track.
- *Rotational Latency*: time for the desired sector to rotate under the head.
- *Transfer Time*: time to actually transfer the data.

**Disk Response Time:**
The time interval between a request being submitted to the disk and the request being serviced (i.e., includes the waiting/queueing time in the disk queue **plus** the disk access time). It reflects how long a user/process must wait after issuing the I/O request.

### 11. Internal vs. External Fragmentation [4+6]

**Differentiation (4 marks):**

| Basis | Internal Fragmentation | External Fragmentation |
|---|---|---|
| Definition | Wasted memory *inside* an allocated partition/block because the allocated block is larger than the requested process size | Wasted memory *between* allocated blocks — free memory exists but is scattered in small non-contiguous pieces |
| Occurs in | Fixed-size partitioning / paging | Variable-size (dynamic) partitioning |
| Cause | Fixed block size doesn't exactly match process size | Processes are allocated and freed at different times, leaving small unusable gaps |
| Example | A process needing 18KB is placed in a 20KB fixed partition → 2KB wasted *inside* the partition | Free blocks of 5KB, 8KB, 4KB exist scattered in memory (total 17KB free), but a process needing 15KB *contiguous* space cannot be allocated even though total free space is sufficient |

**Removal Procedures (6 marks):**

**To reduce/remove Internal Fragmentation:**
1. **Use variable-size partitioning** instead of fixed-size partitions, so memory allocated matches process size exactly.
2. **Use smaller page/block sizes** in paging systems (though very small pages increase page-table overhead, so a balance is needed).
3. Use **Best-Fit allocation** to minimize leftover space inside a block.

**To reduce/remove External Fragmentation:**
1. **Compaction** – Periodically shuffle memory contents to combine all scattered free blocks into one large contiguous block (this requires relocatable code and has a runtime overhead).
   - *Example*: If free blocks of 10K, 15K, and 5K are scattered between allocated processes, compaction moves all processes together, merging the free space into one 30K contiguous block.
2. **Paging** – Divide physical memory into fixed-size frames and logical memory into equal-size pages; since allocation happens frame-by-frame rather than needing contiguous space, external fragmentation is eliminated entirely (though internal fragmentation may occur in the last page).
3. **Segmentation with Paging** – Combine both techniques to get logical structuring of segmentation while avoiding external fragmentation via paging.
