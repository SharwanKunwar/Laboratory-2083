## Q2. Explain different types of kernels.

The **kernel** is the core of an operating system. It runs in privileged mode and manages the CPU, memory, devices and system calls. Kernels are classified by how much functionality runs inside kernel space.

### 1. Monolithic Kernel
- The whole OS (process management, memory management, file system, device drivers, IPC) runs in a single address space in kernel mode.
- **Advantages:** very fast, because services call each other directly with no message passing.
- **Disadvantages:** large and hard to maintain. A bug in one driver can crash the whole system.
- **Examples:** Linux, traditional UNIX, MS-DOS.

### 2. Microkernel
- Only the essential services stay in the kernel: basic scheduling, low-level memory management and IPC.
- File system, drivers and networking run as user-space servers and communicate by message passing.
- **Advantages:** more reliable, secure and easy to extend. A failing service doesn't crash the kernel.
- **Disadvantages:** slower, due to message-passing overhead and context switches.
- **Examples:** Minix, QNX, Mach.

### 3. Hybrid Kernel
- A mix of the two. It keeps a microkernel-like structure but runs some services (e.g. file system, drivers) in kernel space for speed.
- **Examples:** Windows NT/10/11, macOS (XNU).

### 4. Exokernel
- Provides minimal abstraction and only securely multiplexes hardware resources.
- Applications get direct control of hardware through library operating systems.
- **Advantage:** maximum flexibility and performance. **Disadvantage:** complex to use.

### 5. Nanokernel
- An extremely small kernel that provides only hardware abstraction, such as interrupt handling and the timer.

| Feature | Monolithic | Microkernel | Hybrid |
|---|---|---|---|
| Size | Large | Small | Medium |
| Speed | Fast | Slower | Fairly fast |
| Reliability | Low | High | Medium |
| Services run in | Kernel space | User space | Mixed |
| Example | Linux | QNX | Windows NT |

## Q3. What is the Critical Section problem? Explain the Producer-Consumer problem.

### Critical Section Problem
A **critical section** is a segment of code in which a process accesses shared resources (variables, files, tables). If several processes execute their critical sections at the same time, the result depends on the order of execution (a **race condition**).

The **critical section problem** is to design a protocol so that processes can cooperate without corrupting shared data.

General structure of a process:

```
do {
    entry section        // request permission to enter
        critical section // access shared data
    exit section         // release permission
        remainder section
} while (true);
```

A correct solution must satisfy three requirements:
1. **Mutual Exclusion:** if one process is in its critical section, no other process may be in theirs.
2. **Progress:** if no process is in its critical section, the decision on who enters next is made only by processes that want to enter, and cannot be postponed indefinitely.
3. **Bounded Waiting:** there is a limit on how many times others can enter before a waiting process gets its turn (no starvation).

Solutions include Peterson's algorithm, hardware instructions (Test-and-Set), semaphores and monitors.

### Producer-Consumer Problem (Bounded Buffer)
- A **producer** generates items and puts them into a shared buffer of size `N`.
- A **consumer** removes items from the buffer and uses them.
- **Constraints:**
  - The producer must wait if the buffer is **full**.
  - The consumer must wait if the buffer is **empty**.
  - Only one process may access the buffer at a time.

**Solution using semaphores:**

```
semaphore mutex = 1;   // mutual exclusion on buffer access
semaphore empty = N;   // counts empty slots
semaphore full  = 0;   // counts filled slots

Producer:                       Consumer:
do {                            do {
    produce_item();                 wait(full);      // wait if buffer empty
    wait(empty);  // wait if full   wait(mutex);
    wait(mutex);                    remove_item();
    insert_item();                  signal(mutex);
    signal(mutex);                  signal(empty);   // one more empty slot
    signal(full); // one more item  consume_item();
} while (true);                 } while (true);
```

- `empty` blocks the producer when there is no room.
- `full` blocks the consumer when there is nothing to consume.
- `mutex` ensures only one process manipulates the buffer at a time.

## Q5. Compare bitmap and linked list implementation of disk free-space management

**Bitmap (bit vector):** each disk block is represented by one bit. `1` = free, `0` = allocated (or the reverse).
Example: `0011 1100 1000...` shows which blocks are free.

**Linked list:** free blocks are linked together. Each free block holds a pointer to the next free block, and the OS keeps a pointer to the first free block.

| Basis | Bitmap | Linked List |
|---|---|---|
| Representation | One bit per block | Pointer stored inside each free block |
| Extra space | Needs space for the bitmap (e.g. 1 bit per block) | No extra space, uses the free blocks themselves |
| Finding a free block | Fast, scan for first `1` bit (hardware support) | Fast for one block (take the head) |
| Finding contiguous free blocks | Easy | Difficult |
| Traversal / searching | Efficient | Slow, each block must be read to follow the pointers |
| Allocating many blocks | Efficient | Inefficient, needs many disk reads |
| Reliability | A corrupted bitmap affects many blocks | A broken pointer loses the rest of the list |
| Memory use | Large disks need a large bitmap | Only the head pointer is kept in memory |
| Used in | Modern file systems (ext, NTFS) | Simple systems (e.g. older FAT-like schemes) |

**Conclusion:** bitmaps are simpler and faster for finding contiguous space, but need extra memory on large disks. Linked lists use no extra space but are slow to traverse.

## Q6. Authorization and Authentication; Cryptography with encryption and decryption

### Authentication
The process of **verifying the identity** of a user, device or process ("Who are you?").
- Methods: password/PIN, biometrics (fingerprint, face), smart card/token, OTP, multi-factor authentication.

### Authorization
The process of **determining what an authenticated user is allowed to do** ("What can you access?").
- Examples: file permissions (read/write/execute), access control lists, role-based access.

| Authentication | Authorization |
|---|---|
| Verifies identity | Verifies permissions |
| Done first | Done after authentication |
| Uses passwords, biometrics, OTP | Uses ACLs, roles, policies |
| Example: login to a system | Example: only admin can delete files |

### Cryptography
**Cryptography** is the science of securing information by converting it into an unreadable form so that only authorized parties can read it. It provides **confidentiality, integrity, authentication and non-repudiation**.

**Key terms:**
- **Plaintext:** the original readable message.
- **Ciphertext:** the unreadable, encrypted message.
- **Encryption:** converting plaintext to ciphertext using an algorithm and a key.
- **Decryption:** converting ciphertext back to plaintext.
- **Key:** secret value used by the algorithm.

```
Plaintext --[Encryption + Key]--> Ciphertext --[Decryption + Key]--> Plaintext
 (Sender)                            (Channel)                       (Receiver)
```

**Types of cryptography:**

1. **Symmetric-key (secret key):** the same key is used for encryption and decryption.
   - Fast and suitable for large data. The challenge is sharing the key securely.
   - Examples: DES, 3DES, AES.
2. **Asymmetric-key (public key):** two keys, a **public key** (encrypts) and a **private key** (decrypts).
   - No need to share a secret key. Slower than symmetric.
   - Examples: RSA, ECC.
3. **Hash functions:** one-way functions producing a fixed-size digest, used for integrity checks (e.g. SHA-256).

**Example (Caesar cipher, shift = 3):**
Plaintext `HELLO` -> Ciphertext `KHOOR` (encryption). Shifting back by 3 recovers `HELLO` (decryption).

## Q7. Distributed Operating System; advantages over centralized system

### Distributed Operating System
A **distributed operating system** manages a collection of independent, networked computers and makes them appear to users as a **single coherent system**. Processes, files and resources are spread across multiple machines that communicate by message passing, and the OS handles coordination transparently.

**Characteristics:** resource sharing, transparency (location, access, migration, replication, failure), concurrency, scalability, fault tolerance.
**Examples:** LOCUS, Amoeba, Plan 9, Sprite.

### Advantages of a Distributed System over a Centralized System
1. **Resource sharing:** users can use hardware, files and data on other machines.
2. **Reliability / fault tolerance:** if one node fails, others continue. A centralized system has a single point of failure.
3. **Higher performance and speed:** work is divided among many processors (parallel processing).
4. **Scalability:** capacity grows by adding more nodes, with no need to replace the central machine.
5. **Cost effectiveness:** many cheap computers can give a better price/performance ratio than one large mainframe.
6. **Load balancing:** work can be moved from busy nodes to idle ones.
7. **Availability and data replication:** copies of data on different sites keep it available.
8. **Geographic distribution and communication:** supports users and resources at different locations.

### CPU Scheduling Criteria
1. **CPU utilization:** keep the CPU as busy as possible (ideally 40% to 90%).
2. **Throughput:** number of processes completed per unit time.
3. **Turnaround time:** total time from submission to completion (`TAT = Completion Time - Arrival Time`).
4. **Waiting time:** total time spent waiting in the ready queue (`WT = TAT - Burst Time`).
5. **Response time:** time from submission until the first response is produced (first time on CPU).
6. **Fairness:** every process gets a fair share of the CPU.

## Q10. Deadlock, conditions for deadlock, Banker's algorithm

### Deadlock
A **deadlock** is a situation in which a set of processes are all blocked, each holding a resource and waiting for a resource held by another process in the set. None can proceed.

*Example:* P1 holds R1 and waits for R2, while P2 holds R2 and waits for R1.

### Necessary Conditions (Coffman conditions)
All four must hold at the same time for a deadlock to occur:
1. **Mutual exclusion:** at least one resource is non-sharable (only one process can use it at a time).
2. **Hold and wait:** a process holding at least one resource is waiting to acquire more resources held by others.
3. **No preemption:** a resource can be released only voluntarily by the process holding it.
4. **Circular wait:** a cycle of processes exists where each waits for a resource held by the next (P0 -> P1 -> ... -> Pn -> P0).

### Banker's Algorithm (deadlock avoidance)
Before granting a request, the OS checks whether the system will remain in a **safe state** (a safe sequence exists in which every process can finish).

**Data structures** (n processes, m resource types):
- `Available[m]`: free instances of each resource
- `Max[n][m]`: maximum demand of each process
- `Allocation[n][m]`: currently allocated resources
- `Need[n][m] = Max - Allocation`

**Safety algorithm:**
1. `Work = Available`, `Finish[i] = false` for all i.
2. Find i such that `Finish[i] = false` and `Need[i] <= Work`. If none, go to step 4.
3. `Work = Work + Allocation[i]`, `Finish[i] = true`, go to step 2.
4. If `Finish[i] = true` for all i, the system is **safe**.

**Resource-request algorithm (process Pi requests `Request[i]`):**
1. If `Request <= Need[i]` continue, else error (exceeds maximum claim).
2. If `Request <= Available` continue, else Pi must wait.
3. Pretend to allocate: `Available -= Request`, `Allocation[i] += Request`, `Need[i] -= Request`. If the resulting state is safe, grant it; otherwise restore the old state and make Pi wait.

### Example
5 processes (P0 to P4), 3 resource types A, B, C with totals A=10, B=5, C=7.

| Process | Allocation (A B C) | Max (A B C) | Need = Max - Alloc |
|---|---|---|---|
| P0 | 0 1 0 | 7 5 3 | 7 4 3 |
| P1 | 2 0 0 | 3 2 2 | 1 2 2 |
| P2 | 3 0 2 | 9 0 2 | 6 0 0 |
| P3 | 2 1 1 | 2 2 2 | 0 1 1 |
| P4 | 0 0 2 | 4 3 3 | 4 3 1 |

`Available = (3, 3, 2)`

**Safety check:**

| Step | Process chosen | Condition | Work after |
|---|---|---|---|
| 1 | P1 | Need (1,2,2) <= (3,3,2) | (3,3,2)+(2,0,0) = (5,3,2) |
| 2 | P3 | Need (0,1,1) <= (5,3,2) | (5,3,2)+(2,1,1) = (7,4,3) |
| 3 | P4 | Need (4,3,1) <= (7,4,3) | (7,4,3)+(0,0,2) = (7,4,5) |
| 4 | P0 | Need (7,4,3) <= (7,4,5) | (7,4,5)+(0,1,0) = (7,5,5) |
| 5 | P2 | Need (6,0,0) <= (7,5,5) | (7,5,5)+(3,0,2) = (10,5,7) |

All processes can finish, so the system is **safe** with safe sequence **<P1, P3, P4, P0, P2>**.

**Request example:** P1 requests (1,0,2).
- (1,0,2) <= Need (1,2,2) and (1,0,2) <= Available (3,3,2), so pretend to allocate.
- New state: Available = (2,3,0), P1 Allocation = (3,0,2), P1 Need = (0,2,0).
- Running the safety algorithm again finds the safe sequence <P1, P3, P4, P0, P2>, so the request **is granted**.

## Q11. Memory fragmentation, coalescing and compaction, multithreading

### Memory Fragmentation
**Fragmentation** is the wastage of memory that occurs when free memory is broken into small pieces that cannot be used effectively.

1. **Internal fragmentation:** memory wasted *inside* an allocated block because the block is larger than requested (fixed partitioning, paging).
   *Example:* a 10 KB partition given to a 7 KB process wastes 3 KB inside it.
2. **External fragmentation:** enough total free memory exists, but it is scattered in non-contiguous holes, so a request cannot be satisfied (variable partitioning, segmentation).
   *Example:* free holes of 10 KB, 20 KB and 30 KB (60 KB total) cannot satisfy a 50 KB request.

### Coalescing
**Coalescing** merges **adjacent free blocks** into a single larger free block, usually when a process terminates or frees memory.

*Example:*
```
Before: | P1 | Free 20KB | Free 30KB | P2 |      (two adjacent holes)
After : | P1 |       Free 50KB       | P2 |      (merged by coalescing)
```
It reduces external fragmentation but only joins holes that are already neighbours.

### Compaction
**Compaction** shifts the allocated processes toward one end of memory so that all free holes combine into **one large contiguous block**. It requires dynamic relocation (execution-time address binding), and it costs CPU time.

*Example:*
```
Before: | OS | P1 | Free 10KB | P2 | Free 20KB | P3 | Free 30KB |
After : | OS | P1 | P2 | P3 |           Free 60KB               |
```
A 50 KB process that could not be loaded before can now be loaded.

| Coalescing | Compaction |
|---|---|
| Joins adjacent free blocks | Moves processes to gather all free space |
| No process movement | Processes are relocated |
| Cheap and simple | Expensive, needs relocation support |
| Partial solution | Removes external fragmentation fully |

### How Multithreading Improves Performance over a Single-Threaded Solution
A **thread** is a lightweight unit of execution; a process may contain many threads sharing code, data and files, each with its own registers and stack.

1. **Responsiveness:** a program stays interactive even when one thread is blocked or busy. *Example:* in a browser, the UI thread stays responsive while another thread downloads a page. A single-threaded program would freeze.
2. **Resource sharing:** threads share the process's memory and resources by default, so communication is easy and fast.
3. **Economy:** creating threads and context-switching between them is cheaper than for processes.
4. **Better CPU utilization:** while one thread waits for I/O, another can use the CPU.
5. **Scalability and parallelism:** on multicore processors, threads run truly in parallel, so throughput rises. A single-threaded process uses only one core.
6. **Higher throughput:** a web server can handle many client requests at once with one thread per request.

*Example:* a word processor uses one thread for typing input, one for spell-checking and one for auto-saving. All three proceed at the same time instead of one after another.
